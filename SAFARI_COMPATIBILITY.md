# Safari compatibility

This suite runs on Chrome (the default) and Safari, selected with `--variable BROWSER:safari`. This page lists which tests run on Safari, which run through a Safari-specific fallback, and which are skipped and why.

The table below is generated by `tools/safari_compatibility.py`. The tool walks every test case with `robot.api`, recursing into the keywords of `ressources.robot` and each suite's own keywords, and simulates the shared browser session between the tests of a suite. Regenerate it after changing tests:

```
python tools/safari_compatibility.py --markdown SAFARI_COMPATIBILITY.md
python tools/safari_compatibility.py --check    # the tags in the .robot files must match
```

## Statuses and tags

- **RUN**: runs on Safari through the same keywords as Chrome.
- **RUN-WITH-FALLBACK**: runs on Safari through a browser-specific branch:
  - the marker image is uploaded instead of taken with the camera (`Provide Marker Image`);
  - a CSS-hidden file input is unhidden before `Choose File` (`Choose File Robust`);
  - or the test uses drag and drop, which has no Safari-specific code.
- **SKIP**: tagged `chrome-only` plus one or more `safari-skip:<reason>` tags. Safari runs pass `--exclude chrome-only`. If a tagged test is run on Safari anyway, the suite's `Test Setup` (`Skip Chrome-Only Test On Safari`) reports SKIP with the reason instead of failing.
- **`safari-unverified`**: every test that is not skipped. None of the Safari paths has been executed yet, because this work was done on Windows. Remove the tag from a suite once a Safari run has proven it.

## Known limitations on Safari

- **No fake camera or microphone.** Chrome streams `assets/fakecamfeed_cortez.y4m` and `assets/moo1.wav` through `--use-fake-device-for-media-stream`; Safari has no equivalent.
  - `Provide Marker Image` uploads `assets/fakecamfeed_cortez.png` (a frame of the same feed) through the wizard's "upload image" control instead of snapping a photo.
  - The step sequence after an upload has no "Validate the image" step. That sequence is only evidenced for **Augmented activity** (051) and **Search and Find** (`Create failed search and find activity`). Information layers and the Pair Association camera flow (004) are `safari-skip:camera-todo`; Pair Association is still covered on Safari through its upload flow (037, 072).
  - Anything that needs a live camera image is skipped: marker detection ("Well done!", 035), microphone recording (041, 045), and onboarding tours whose steps target the camera controls (070, 073).
  - `Wait For Detection Or Log Miss` already tolerates a missed detection with a WARN, so the editors' "display activity" steps still run.
- **No network emulation.** `Go Offline`, `Go Online`, `Set Network Speed` and `Reset Network Speed` use `execute_cdp_cmd` (Chrome DevTools Protocol). On Safari they SKIP the test. Every offline suite and every "– Slow 3G" chain is `chrome-only`. The later tests of a chain inherit the throttled session without calling CDP themselves, which is why they carry `safari-skip:cdp-state`.
- **`navigator.onLine` semantics.** CDP's `offline=true` makes the browser itself report offline (`navigator.onLine === false`, `offline` events, failing fetches). Any future Safari offline approach at the OS or network level only makes requests fail; WebKit may keep `navigator.onLine` true (for example on a local network without internet). The app's offline UI, such as local-draft badges and sync status, may therefore behave differently, and results would not be directly comparable with the Chrome offline suites.
- **One WebDriver session per machine.** safaridriver refuses a second concurrent session. `Open MIXAP Browser` closes any leftover session before opening Safari. Suites 043, 049 and 054, which hold two browsers (`Open Web Application with alias` + `Switch Browser`), are `safari-skip:concurrent-browsers`. Local parallel batches are Chrome-only; `run_safari.sh` runs sequentially. In CI each matrix batch is its own VM, so batches still run in parallel there.
- **Hidden file inputs.** On Safari, `Choose File Robust` unhides the Ant Design upload `input[type=file]` with JavaScript before `Choose File`. Not yet executed on Safari.
- **Drag and drop.** It is not confirmed which events the app listens for (pointer/mouse vs HTML5 drag-and-drop), so Safari runs the same Selenium action chain as Chrome with no JavaScript fallback. Affected callers: `Add Activity to Path`, `Add Activity to Path By Id` and `Create failed search and find activity` (021, 028, 032, 036, 066, 067 on Safari; 046 also drags but is chrome-only).
- **`Bypass https alert`** clicks ids of Chrome's own certificate interstitial page. It is Chrome-only and currently unused.

## Future work

- **Offline and throttling on Safari:** emulate them at the OS level on macOS with `pfctl` (block traffic to the preprod host) and `dnctl`/dummynet pipes (latency and bandwidth for "Slow 3G"). This would need sudo on the runner and a keyword pair that shells out to them in place of the CDP calls. Mind the `navigator.onLine` difference above.
- **Suites 043, 049 and 054:** restructure them to run sequentially in one session. Sign in as account 1 and act, then sign out; sign in as account 2 and act; and so on. They could then run on Safari.
- **iOS Safari:** safaridriver supports the iOS Simulator through the `safari:useSimulator` capability (plus `platformName: iOS`), which would exercise the PWA on its main mobile target.
- **Camera TODOs:** determine the upload-path step sequence for Information layers and Pair Association from a live run, then extend `Provide Marker Image`.
- **Verification:** run the Safari CI job and remove `safari-unverified` suite by suite as they pass. Classify each Safari failure as either test code incompatible with Safari (fix it) or a possible MIXAP bug on Safari (record the evidence from log.html, do not work around it).
